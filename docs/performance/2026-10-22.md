# Website response-time improvements — 22 October 2026

## Changes

- Both Vercel projects run Functions in Frankfurt (`fra1`), near the existing Neon database. Region is also tracked in each app's `vercel.json`.
- The public root layout now lives under `[locale]`. The URL supplies `html.lang` without reading request headers. About, Contact and legal pages are prerendered for all six languages; unmatched routes retain a styled 404 with noindex.
- Contact query prefills are resolved by a client component under Suspense. A default form remains in the prerendered HTML; existing service aliases, request modes and public references are validated.
- Active public prices use a 60-second stale-while-revalidate Data Cache. These pages stay dynamic to avoid an additional page-cache freshness window. Outage fallbacks are not persisted in the Data Cache.
- Project/product publication checks remain live. Internal WebP derivatives are generated once per immutable image ID/width and reused for a day. Every media response remains private/no-store and every request checks publication, image archival and product rights before reading the cached derivative.
- Session lookup and dashboard counters are deduplicated within a React server render, never across requests. Private dashboard responses remain uncached. A loading boundary provides immediate route-transition feedback.

## Validation

- Both production builds and workspace TypeScript checks passed.
- 17 focused tests passed; one database release regression test was skipped because its dedicated local fixture was not configured. The real release schema guard is still part of the Control deployment.
- An isolated Neon rehearsal branch was used for authenticated dashboard/API smoke checks; no production login/session/test records were created.
- Six localized contact pages returned prerendered HTML with the correct `html.lang`; invalid paths returned 404 and noindex.
- Repeated public project and product thumbnails returned identical WebP bytes. Warming a derivative and then archiving its image or removing product rights immediately returned 404.
- Test-only users, sessions, projects and products were removed from the rehearsal branch afterward.

## Timing evidence and limitations

Local production servers with the same isolated remote database transport, one warm-up and three samples per route:

| Route | Previous median | Updated median |
| --- | ---: | ---: |
| Dashboard | 766 ms | 526 ms |
| Customers | 675 ms | 504 ms |
| Inbox | 554 ms | 899 ms |
| Invoices | 1555 ms | 1520 ms |
| Projects | 1200 ms | 1276 ms |

These small samples show network variance and do not establish a universal speedup. They exclude the deployed Frankfurt-region benefit. Public About and Contact completed in 7 ms and 6 ms respectively on the updated local server. The updated price page completed in 17 ms with a warm Data Cache.

For a test image, the updated project thumbnail took 1409 ms on its first uncached request and 120 ms warm; the product thumbnail took 681 ms first and 119 ms warm. This is a cold-versus-warm comparison of the updated code, not a before-versus-after production benchmark.

Initial public HTTP measurements used an egress proxy that added several seconds even for a cached SVG. Do not use those raw totals as end-user latency or Lighthouse/Core Web Vitals scores. No field LCP/INP/CLS claims are made.
